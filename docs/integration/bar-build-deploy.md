# Ory Hydra — Build & Deploy Integration with Bar Ecosystem

How to build Hydra via GoReleaser, push the Docker image to ECR, and deploy it
from the bar monorepo using Pulumi. Follows the same patterns used by
`bar/eudi` (oidc4vp-connector, oidc4vp-verifier, etc.).

---

## Architecture Overview

```
┌─────────────────────────────────────────────────────────────────────┐
│  HYDRA REPO (build + push)                                          │
│                                                                      │
│  .goreleaser.yml                                                     │
│    builds: hydra binary (linux/amd64 + linux/arm64)                  │
│    dockers_v2: multi-arch image → ECR (ory/hydra)                    │
│                                                                      │
│  CI: GitHub Actions                                                  │
│    on tag push → goreleaser release → push to ECR                    │
│    on snapshot → goreleaser release --nightly → push to preview ECR  │
│                                                                      │
│  Output: Docker image in ECR at                                      │
│    <account>.dkr.ecr.eu-central-1.amazonaws.com/ory/hydra:<version>  │
└─────────────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────────────┐
│  BAR REPO (deploy)                                                   │
│                                                                      │
│  cfg/registry.yaml                                                   │
│    ory project: ecr: [hydra]  ← already registered                   │
│                                                                      │
│  Pulumi deploy programs (per environment):                           │
│    hydra/deploy/{sandbox,devel,stage,prod}/main.go                   │
│    Load artifacts from lock files → deploy K8s Deployment + DB       │
│                                                                      │
│  Artifact lock files (GitOps):                                       │
│    hydra/deploy/<env>/ory.forge.lock.yaml                            │
│    Generated by: barctl artifacts snapshot (or stable)               │
└─────────────────────────────────────────────────────────────────────┘
```

## Part 1: Build & Push (Hydra Repo)

### 1.1 Current State

Hydra already has a working GoReleaser setup:

| File | Purpose |
|---|---|
| `.goreleaser.yml` | Builds `hydra` binary, produces multi-arch Docker image via `dockers_v2` |
| `.docker/Dockerfile-goreleaser` | Distroless image, copies pre-built binary per `$TARGETPLATFORM` |

The current config pushes to `oryd/hydra` (Docker Hub). For bar ecosystem
integration, the image must also be pushed to ECR.

### 1.2 Required Changes to `.goreleaser.yml`

Add a second `dockers_v2` entry that pushes to ECR. The `REGISTRY` env var is
injected by `barctl artifacts` (or by the CI workflow directly).

```yaml
dockers_v2:
  # Existing: local/Docker Hub image (keep for open-source compatibility)
  - id: hydra
    ids: [hydra]
    dockerfile: .docker/Dockerfile-goreleaser
    images:
      - oryd/hydra
    tags:
      - "{{ .Version }}"
      - "{{ if not .IsSnapshot }}latest{{ end }}"
    platforms:
      - linux/amd64
      - linux/arm64
    labels:
      org.opencontainers.image.title: hydra
      org.opencontainers.image.version: "{{ .Version }}"
      org.opencontainers.image.revision: "{{ .Commit }}"
      org.opencontainers.image.created: "{{ .Date }}"

  # New: ECR image for bar ecosystem deployment
  - id: hydra-ecr
    ids: [hydra]
    dockerfile: .docker/Dockerfile-goreleaser
    images:
      - "{{ .Env.REGISTRY }}/ory/hydra"
    tags:
      - "{{ .Version }}"
      - "{{ if not .IsSnapshot }}latest{{ end }}"
    platforms:
      - linux/amd64
      - linux/arm64
    labels:
      org.opencontainers.image.title: hydra
      org.opencontainers.image.version: "{{ .Version }}"
      org.opencontainers.image.revision: "{{ .Commit }}"
      org.opencontainers.image.created: "{{ .Date }}"
```

The `REGISTRY` variable resolves to the ECR URL, e.g.:
- Preview: `677224894277.dkr.ecr.eu-central-1.amazonaws.com`
- Stable: `721506300184.dkr.ecr.eu-central-1.amazonaws.com`

Image path in ECR: `<account>.dkr.ecr.eu-central-1.amazonaws.com/ory/hydra`

This matches the `ory` project with `hydra` component in `cfg/registry.yaml`.

### 1.3 CI Workflow for ECR Push

Add a new GitHub Actions workflow (or job in the existing `ci.yaml`) that builds
and pushes to ECR. This runs on the bar CI infrastructure (self-hosted runners
with ECR credentials via IRSA).

**Option A: Run from bar CI (recommended)**

The bar repo's CI pipeline already knows how to authenticate to ECR and run
goreleaser. Add Hydra as a project in `cfg/projects.yaml`:

```yaml
# cfg/projects.yaml (bar repo)
- name: ory
  kind: go-only
  purpose: Ory Hydra OAuth2/OIDC server (external repo, ECR mirror)
  team: Backend
  goreleaser: hydra  # points to hydra/ directory (git submodule or checkout)
```

Then `barctl artifacts snapshot ory` or `barctl artifacts stable ory` handles
the full pipeline: goreleaser → ECR push → artifact lock file generation.

**Option B: Run from Hydra CI (standalone)**

If Hydra CI must be self-contained, add a workflow job that authenticates to ECR
and runs goreleaser with the `REGISTRY` env var:

```yaml
# .github/workflows/ecr-push.yaml (hydra repo)
name: Push to ECR
on:
  push:
    tags: ["*"]
  workflow_dispatch:
    inputs:
      snapshot:
        description: "Build snapshot (nightly)"
        type: boolean
        default: false

jobs:
  push-ecr:
    runs-on: ci-stable  # bar self-hosted runner with ECR access
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0

      - uses: actions/setup-go@v6
        with:
          go-version-file: go.mod

      - name: Configure AWS credentials
        uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: ${{ secrets.ECR_PUSH_ROLE_ARN }}
          aws-region: eu-central-1

      - name: Login to ECR
        uses: aws-actions/amazon-ecr-login@v2

      - name: Run GoReleaser
        env:
          REGISTRY: ${{ secrets.ECR_REGISTRY_URL }}
        run: |
          if [ "${{ inputs.snapshot }}" = "true" ]; then
            goreleaser release --nightly --clean -f .goreleaser.yml
          else
            goreleaser release --clean -f .goreleaser.yml
          fi
```

### 1.4 ECR Repository

The ECR repository `ory/hydra` is already declared in `cfg/registry.yaml`:

```yaml
# cfg/registry.yaml (bar repo) — already exists
- name: ory
  ecr:
    - hydra
  s3: []
```

The registry Pulumi stack (`nexus/`) creates ECR repositories from this config.
No changes needed — the `ory/hydra` repo already exists in both preview and
stable accounts.

### 1.5 Cross-Repo Build: How barctl Builds Hydra from Bar

Hydra lives in a separate Git repository, not inside the bar monorepo. The
`barctl artifacts` command expects a `.goreleaser.yaml` file inside the bar
repo's directory tree. There are two practical approaches to bridge this:

**Approach A: Git Submodule (recommended)**

Add the Hydra repo as a Git submodule inside bar:

```bash
# In bar repo root
git submodule add git@github.com:<org>/hydra.git hydra
```

This creates `bar/hydra/` containing the full Hydra source. The
`cfg/projects.yaml` entry points to it:

```yaml
- name: ory
  kind: go-only
  purpose: Ory Hydra OAuth2/OIDC server (external fork)
  team: Backend
  goreleaser: hydra   # → bar/hydra/.goreleaser.yml
```

When `barctl artifacts snapshot ory` runs, it:
1. Resolves `goreleaser: hydra` → `<git-root>/hydra/.goreleaser.yml`
2. Runs `goreleaser release --nightly --clean -f hydra/.goreleaser.yml` from
   the git root
3. GoReleaser builds the binary from `hydra/` source, produces Docker images,
   pushes to ECR via the `REGISTRY` env var
4. Generates `dist/ory.forge.lock.yaml` with the image digest

The submodule is pinned to a specific commit. To update Hydra:

```bash
cd hydra && git fetch && git checkout <tag-or-commit> && cd ..
git add hydra
git commit -m "chore: bump hydra to <version>"
```

**Approach B: CI Checkout (no submodule)**

If submodules are undesirable, the CI workflow checks out Hydra into the
expected path before running barctl:

```yaml
# .github/workflows/hydra-build.yaml (bar repo)
steps:
  - uses: actions/checkout@v4  # bar repo
  - uses: actions/checkout@v4
    with:
      repository: <org>/hydra
      ref: ${{ inputs.hydra_ref }}
      path: hydra
  - run: barctl artifacts snapshot ory
```

This is simpler to set up but loses the GitOps property — the Hydra version
isn't tracked in bar's git history. Submodule is preferred for production.

**Why not build from Hydra CI directly?**

Building from bar CI is preferred because:
- `barctl` handles ECR authentication, registry URL resolution, S3 bucket
  selection, and artifact lock file generation automatically
- The goreleaser `REGISTRY` env var, `AWS_PROFILE`, `S3_BUCKET`, and
  `AWS_REGION` are all injected by barctl from `cfg/registry.yaml` and
  `cfg/topology.yaml`
- Lock files are generated in `dist/` and can be committed to bar for GitOps
- No need to duplicate AWS credential configuration in the Hydra repo

### 1.6 Fork Versioning

This Hydra repo is a fork of upstream `ory/hydra`. The fork adds OIDC4VCI
extensions (Pre-Authorized Code, DPoP, PAR persistence, Wallet Attestation,
HAIP, RAR) that are not in upstream.

**Version format:**

GoReleaser derives the version from Git tags. The fork uses a version format
that encodes both the upstream base version and the fork release number:

```
v<base>-oidc4vci.<fork_release>
```

Where:
- `<base>` is the upstream Ory Hydra semver version the fork is based on
- `<fork_release>` is a monotonically increasing integer for each fork release
  on that base version

Examples:
- `v2.3.0-oidc4vci.1` — first fork release on upstream 2.3.0
- `v2.3.0-oidc4vci.2` — second fork release on upstream 2.3.0
- `v26.1.0-oidc4vci.1` — first fork release on upstream 26.1.0

When the fork is rebased onto a new upstream version, the fork release counter
resets to 1 (e.g., moving from `v2.3.0-oidc4vci.3` to `v2.4.0-oidc4vci.1`).

The version format is a valid semver pre-release identifier per SemVer 2.0.0 §9,
ensuring compatibility with GoReleaser, Docker tag rules, and `barctl artifacts`
lock file generation.

**Snapshot versions:**

When `barctl artifacts snapshot ory` runs (no tag on HEAD), GoReleaser uses the
`snapshot.version_template` from `.goreleaser.yml`:

```yaml
snapshot:
  version_template: "local"
```

This produces images tagged `local-amd64` / `local-arm64`. For nightly CI
builds, GoReleaser's `--nightly` flag generates a version like
`<next-version>-<shortcommit>-nightly` (e.g., `2.3.0-oidc4vci.2-abc1234-nightly`).

**GoReleaser monorepo tag prefix:**

The `monorepo.tag_prefix` field is not used — Hydra is a standalone repository
with its own tag namespace. Tags live in the Hydra repo directly, not in the
bar repo.

**ldflags version injection:**

The `.goreleaser.yml` injects version info via ldflags:

```yaml
ldflags:
  - -X github.com/ory/hydra/v2/driver/config.Version={{.Version}}
  - -X github.com/ory/hydra/v2/driver/config.Commit={{.Commit}}
  - -X github.com/ory/hydra/v2/driver/config.Date={{.Date}}
```

These variables are defined in `oryx/` (the vendored `ory/x` dependency). The
`hydra version` CLI command and the `/health/alive` endpoint report these
values. For a fork tag like `v2.3.0-oidc4vci.1`, `hydra version` reports
`2.3.0-oidc4vci.1` (GoReleaser strips the `v` prefix automatically).

## Part 2: Deploy (Bar Repo)

### 2.1 Artifact Lock Files

After building, `barctl artifacts` generates lock files that pin the exact image
digest. These are committed to the bar repo for GitOps deployment.

Example `ory.forge.lock.yaml`:

```yaml
# Generated by: barctl artifacts ory
# DO NOT EDIT
version: "1"
components:
  hydra:
    version: "2.3.0"
    source: snapshot
    purl: "pkg:oci/hydra@sha256:abc123...?repository_url=677224894277.dkr.ecr.eu-central-1.amazonaws.com/ory"
    artifacts:
      multi:
        url: "677224894277.dkr.ecr.eu-central-1.amazonaws.com/ory/hydra@sha256:abc123..."
        registry: "677224894277.dkr.ecr.eu-central-1.amazonaws.com"
        repository: "ory/hydra"
        digest: "sha256:abc123..."
        tags: ["2.3.0"]
```

Lock files live at:
- `hydra/deploy/sandbox/ory.forge.lock.yaml` (snapshot builds)
- `hydra/deploy/devel/ory.forge.lock.yaml` (committed, GitOps)
- `hydra/deploy/stage/ory.forge.lock.yaml`
- `hydra/deploy/prod/ory.forge.lock.yaml`

### 2.2 Pulumi Artifact Loading

Follow the same pattern as `eudi/pkg/pulumi/artifacts.go`. Create a Hydra
artifact loader in the bar repo:

```go
// bar/hydra/pkg/pulumi/artifacts.go
package pulumi

import (
    "context"
    "fmt"
    "log/slog"
    "strings"

    deploycommon "github.com/truvity/bar/bar/pkg/deploy-common"
)

var hydraComponents = map[string]deploycommon.ComponentSpec{
    "hydra": {Docker: true},
}

type ResolvedArtifacts struct {
    Hydra *deploycommon.ArtifactConfig
}

func LoadArtifacts(ctx context.Context, logger *slog.Logger, baseDir string) (*ResolvedArtifacts, error) {
    specs := []deploycommon.ProjectSpec{
        {
            LockFile:   "ory.forge.lock.yaml",
            BaseDir:    baseDir,
            Project:    "ory",
            Components: hydraComponents,
        },
    }

    loaded, err := deploycommon.LoadMultiProject(ctx, logger, specs)
    if err != nil {
        return nil, fmt.Errorf("load artifacts: %w", err)
    }

    imageURI := loaded.MustGetDocker("ory", "hydra")
    parts := strings.SplitN(imageURI, "@", 2)
    image := parts[0]
    digest := ""
    if len(parts) > 1 {
        digest = parts[1]
    }

    return &ResolvedArtifacts{
        Hydra: &deploycommon.ArtifactConfig{
            Type:   deploycommon.ArtifactTypeDocker,
            Image:  image,
            Digest: digest,
        },
    }, nil
}
```

### 2.3 Pulumi Deploy Program

Each environment gets a deploy program. Follow the `eudi/deploy/` pattern.

```
bar/
  hydra/
    deploy/
      sandbox/main.go    # User-prefixed stacks, snapshot builds
      devel/main.go      # primary-hydra stack, committed lock files
      stage/main.go      # primary-hydra stack, committed lock files
      prod/main.go       # primary-hydra stack, committed lock files
    pkg/
      pulumi/
        artifacts.go     # Artifact loading (above)
        deploy.go        # K8s deployment logic
        config.go        # Hydra-specific config (ports, env vars, etc.)
```

Minimal deploy program (devel example):

```go
// bar/hydra/deploy/devel/main.go
package main

import (
    "fmt"
    "log/slog"
    "os"

    "github.com/pulumi/pulumi/sdk/v3/go/pulumi"

    bardeploy "github.com/truvity/bar/bar/pkg/bar-deploy"
    barloader "github.com/truvity/bar/bar/pkg/bar-loader"
    pulumiaws "github.com/truvity/bar/bar/pkg/pulumi-manager-aws"
    pulumik8s "github.com/truvity/bar/bar/pkg/pulumi-manager-k8s"
    pulumihydra "github.com/truvity/bar/hydra/pkg/pulumi"
)

func main() {
    logger := slog.New(slog.NewTextHandler(os.Stderr, &slog.HandlerOptions{
        Level: slog.LevelInfo,
    }))

    pulumi.Run(func(c *pulumi.Context) error {
        cfg, err := barloader.Load(c.Context(), logger)
        if err != nil {
            return fmt.Errorf("load config: %w", err)
        }

        deploy := bardeploy.NewDeployContext("hydra", "primary",
            bardeploy.WithConfig(cfg),
            bardeploy.WithAccount("devel"),
            bardeploy.WithProfile(pulumiaws.AccountProfilePower("devel")),
            bardeploy.WithNamespace("hydra"),
        )

        artifacts, err := pulumihydra.LoadArtifacts(
            c.Context(), logger, "hydra/deploy/devel",
        )
        if err != nil {
            return fmt.Errorf("load artifacts: %w", err)
        }

        // Deploy Hydra K8s resources (Deployment, Service, ConfigMap, etc.)
        // using artifacts.Hydra.Image + artifacts.Hydra.Digest
        return pulumihydra.DeployK8s(c, deploy, logger, artifacts)
    })
}
```

### 2.5 K8s Deployment Resources

Hydra needs:

| Resource | Purpose |
|---|---|
| Deployment | Hydra `serve all` (public 4444 + admin 4445) |
| Service (public) | ClusterIP or LoadBalancer for port 4444 |
| Service (admin) | ClusterIP for port 4445 (internal only) |
| ConfigMap | `hydra.yml` configuration |
| Secret | `SECRETS_SYSTEM`, `DSN`, etc. (from Secrets Manager via ESO) |
| Job (migrate) | `hydra migrate sql -e --yes` (runs before deployment) |
| ServiceAccount | IRSA for AWS access (Secrets Manager, RDS IAM auth) |

The Pulumi deploy module (`hydra/pkg/pulumi/deploy.go`) creates these resources
using the `pulumi-k8s` helpers from the bar framework, same as
`eudi/pkg/pulumi/k8s.go`.

## Part 3: Hydra Configuration

### 3.1 Where Configuration Lives

Hydra reads configuration from a YAML file and/or environment variables. In the
bar ecosystem, configuration is split across two layers:

| Layer | What | Where |
|---|---|---|
| ConfigMap | Non-secret YAML config (`hydra.yml`) | Pulumi creates K8s ConfigMap, mounted at `/etc/config/hydra/hydra.yml` |
| K8s Secret | Secrets (`DSN`, `SECRETS_SYSTEM`, etc.) | AWS Secrets Manager → ESO → K8s Secret → env vars |

The Hydra container runs:
```
hydra serve all -c /etc/config/hydra/hydra.yml
```

Environment variables override YAML config (dots become underscores, uppercase).
For example, `secrets.system` → `SECRETS_SYSTEM`.

### 3.2 Configuration Template

The Pulumi deploy module should generate the ConfigMap from a template. The
reference config is `contrib/quickstart/oidc4vci/hydra-local-oidc4vci-config.yml`
in the Hydra repo. A production config differs in these key areas:

```yaml
# Production hydra.yml — non-secret values only
log:
  level: info                    # not debug

dev: false                       # CRITICAL: must be false in production

serve:
  public:
    port: 4444
    host: 0.0.0.0
    cors:
      enabled: true
      allowed_origins:
        - https://oidc4-demo.<env>.truvity.tech
  admin:
    port: 4445
    host: 0.0.0.0
  cookies:
    same_site_mode: Lax
    secure: true                 # HTTPS in production

urls:
  self:
    issuer: https://hydra.<env>.truvity.tech
    public: https://hydra.<env>.truvity.tech
    admin: http://hydra-admin:4445   # internal K8s service
  login: https://consent-app.<env>.truvity.tech/login
  consent: https://consent-app.<env>.truvity.tech/consent
  logout: https://consent-app.<env>.truvity.tech/logout
  error: https://consent-app.<env>.truvity.tech/error

# DSN, secrets.system, secrets.cookie — injected via env vars, NOT in this file

oidc:
  subject_identifiers:
    supported_types: [public, pairwise]
    pairwise:
      salt: <injected-via-env>   # OIDC_SUBJECT_IDENTIFIERS_PAIRWISE_SALT

  access_token: opaque
  scope: exact

    encrypt_at_rest: true

      cost: 12                   # higher than quickstart (4)
  pkce:
    enforced: true
    enforced_for_public_clients: true
  par:
    enforced: true
    context_lifespan: 5m

# OIDC4VCI features
rar:
  enabled: true
  types_supported: [openid_credential]
haip:
  enforced: true
dpop:
  enabled: true
  signing_alg_values_supported: [ES256]
  nonce_enabled: true
  nonce_lifespan: 5m
  proof_max_age: 60s

  iss_parameter_enabled: true

  enabled: true
  lifespan: 30m
  anonymous_access: false

```

The `<env>` placeholders are resolved by the Pulumi deploy module at deploy
time using `pulumi.Sprintf` or Go string formatting.

### 3.3 Per-Environment Overrides

Each environment may override specific values. The Pulumi deploy module should
accept a config struct with environment-specific overrides:

| Setting | sandbox | devel | stage | prod |
|---|---|---|---|---|
| `log.level` | debug | debug | info | info |
| `dev` | true | false | false | false |
| `cookies.secure` | false | true | true | true |
| `bcrypt.cost` | 4 | 10 | 12 | 12 |
| `issuer` | http://... | https://...devel | https://...stage | https://...prod |
| `wallet_attestation.trust_anchors` | test CA | test CA | prod CA | prod CA |

## Part 4: Secrets

### 4.1 Required Secrets

Hydra requires several secrets that must never appear in ConfigMaps or Git.
See `docs/integration/secret-management.md` for the full inventory.

| Secret | Env Var | Min Length | Notes |
|---|---|---|---|
| System secret | `SECRETS_SYSTEM` | 32 chars | HMAC signing + AES encryption key |
| Cookie secret | `SECRETS_COOKIE` | 32 chars | Session cookie encryption |
| Pairwise salt | `OIDC_SUBJECT_IDENTIFIERS_PAIRWISE_SALT` | 8 chars | Immutable after first deploy |
| Database DSN | `DSN` | — | `postgres://...` connection string |

### 4.2 Secret Generation

Generate secrets before the first deployment. Use Pulumi's `random` provider:

```go
systemSecret, err := random.NewRandomPassword(ctx, "hydra-system-secret", &random.RandomPasswordArgs{
    Length:  pulumi.Int(48),
    Special: pulumi.Bool(false),
})

// Store in Secrets Manager
secret, err := secretsmanager.NewSecret(ctx, "hydra-secrets", &secretsmanager.SecretArgs{
    Name: pulumi.Sprintf("hydra/%s/secrets", environment),
})
secretVersion, err := secretsmanager.NewSecretVersion(ctx, "hydra-secrets-version", &secretsmanager.SecretVersionArgs{
    SecretId: secret.ID(),
    SecretString: pulumi.Sprintf(`{
        "system": "%s",
        "cookie": "%s",
        "pairwise_salt": "%s",
        "dsn": "%s"
    }`, systemSecret.Result, cookieSecret.Result, pairwiseSalt.Result, dsnValue),
})
```

### 4.3 Secret Injection via ESO

ExternalSecrets Operator syncs AWS Secrets Manager → K8s Secret:

```yaml
apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: hydra-secrets
spec:
  refreshInterval: 1h
  secretStoreRef:
    name: aws-secrets-manager
    kind: ClusterSecretStore
  target:
    name: hydra-secrets
  data:
    - secretKey: SECRETS_SYSTEM
      remoteRef:
        key: hydra/<env>/secrets
        property: system
    - secretKey: SECRETS_COOKIE
      remoteRef:
        key: hydra/<env>/secrets
        property: cookie
    - secretKey: OIDC_SUBJECT_IDENTIFIERS_PAIRWISE_SALT
      remoteRef:
        key: hydra/<env>/secrets
        property: pairwise_salt
    - secretKey: DSN
      remoteRef:
        key: hydra/<env>/secrets
        property: dsn
```

The Hydra Deployment references this K8s Secret via `envFrom`:

```yaml
envFrom:
  - secretRef:
      name: hydra-secrets
```

### 4.4 Secret Rotation

System and cookie secrets support zero-downtime rotation via comma-separated
arrays. The first value is the active key; subsequent values are kept for
verification/decryption of existing tokens. See `docs/integration/secret-management.md`
for the full rotation procedure.

The pairwise salt is immutable — changing it breaks all pairwise subject
identifiers permanently.

## Part 5: Database Migrations

### 5.1 How Hydra Migrations Work

Hydra uses Pop ORM for SQL migrations. Migration files live in
`persistence/sql/migrations/` with per-dialect variants (`.postgres.up.sql`,
`.mysql.up.sql`, `.cockroach.up.sql`, `.sqlite.up.sql`). There are 300+
migration files spanning from 2019 to 2026, including the OIDC4VCI extensions
(`20260414*` through `20260418*`).

The migration command:
```
hydra migrate sql up -e --yes
```

This reads the DSN from the `DSN` env var (`-e` flag) and applies all pending
migrations without interactive confirmation (`--yes`).

Hydra tracks applied migrations in a `schema_migration` table. Each migration
runs in a transaction (where the dialect supports it). Migrations are
forward-only in production — `migrate sql down` exists but should never be used
in deployed environments.

### 5.2 Migration Risks

Migrations alter the database schema and can break a running Hydra instance if
not handled carefully:

| Risk | Scenario | Mitigation |
|---|---|---|
| Column removal | Migration drops a column that running Hydra still reads | Always migrate before deploying new binary |
| Column addition with NOT NULL | New column without default breaks existing rows | Hydra migrations use nullable columns or defaults |
| Index creation on large table | `CREATE INDEX` locks the table on some engines | Use `autocommit` migration variant (Hydra has these for large tables) |
| Failed migration | Partial migration leaves schema in broken state | Transactions protect individual migrations; restore from backup if needed |
| Rollback impossible | `down` migration may lose data (e.g., dropped column) | Treat migrations as irreversible in production |

### 5.3 Migration Strategy for Deployment

The migration must run as a separate K8s Job that completes before the Hydra
Deployment starts. This is critical — the new Hydra binary may depend on schema
changes that the migration introduces.

```
┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│  DB Backup   │ ──→ │  Migrate Job │ ──→ │  Hydra Deploy│
│  (optional)  │     │  (must pass) │     │  (rolling)   │
└──────────────┘     └──────────────┘     └──────────────┘
```

In Pulumi, enforce ordering with `dependsOn`:

```go
// Migration Job
migrateJob, err := batchv1.NewJob(ctx, "hydra-migrate", &batchv1.JobArgs{
    Metadata: &metav1.ObjectMetaArgs{
        Name:      pulumi.Sprintf("%s-hydra-migrate", releaseName),
        Namespace: pulumi.String(namespace),
    },
    Spec: &batchv1.JobSpecArgs{
        BackoffLimit: pulumi.Int(3),
        Template: &corev1.PodTemplateSpecArgs{
            Spec: &corev1.PodSpecArgs{
                RestartPolicy: pulumi.String("OnFailure"),
                Containers: corev1.ContainerArray{
                    &corev1.ContainerArgs{
                        Name:    pulumi.String("migrate"),
                        Image:   pulumi.String(artifacts.Hydra.Image),
                        Command: pulumi.ToStringArray([]string{"hydra", "migrate", "sql", "up", "-e", "--yes"}),
                        EnvFrom: corev1.EnvFromSourceArray{
                            &corev1.EnvFromSourceArgs{
                                SecretRef: &corev1.SecretEnvSourceArgs{
                                    Name: pulumi.String("hydra-secrets"),
                                },
                            },
                        },
                    },
                },
            },
        },
    },
}, pulumi.Provider(k8sProvider))

// Hydra Deployment depends on migration completing
hydraDeployment, err := appsv1.NewDeployment(ctx, "hydra", &appsv1.DeploymentArgs{
    // ...
}, pulumi.Provider(k8sProvider), pulumi.DependsOn([]pulumi.Resource{migrateJob}))
```

### 5.4 Pre-Deployment Checklist for Migrations

- [ ] Check migration status before deploying: `hydra migrate sql status -e`
- [ ] Take a database snapshot/backup (Aurora: automated, but verify)
- [ ] For stage/prod: review the specific migration SQL files that will run
      (compare current schema version with target)
- [ ] Ensure no other Hydra instances are running migrations concurrently
- [ ] After migration: verify `hydra migrate sql status -e` shows all applied
- [ ] If migration fails: do NOT deploy the new binary; investigate and fix
      or restore from backup

### 5.5 Backward Compatibility Window

When upgrading Hydra, there's a window where the old binary runs against the
new schema (during rolling deployment). Hydra's migrations are designed to be
backward-compatible within a minor version — new columns are nullable or have
defaults, and old columns are not removed in the same release that stops using
them.

However, across major version jumps this is not guaranteed. Always:
1. Migrate first
2. Deploy new binary
3. Never skip versions — apply migrations sequentially

## Part 8: Production Hardening

Deploying the Hydra fork to production requires hardening beyond what the
quickstart config provides. This section covers the delta between
`contrib/quickstart/oidc4vci/hydra-local-oidc4vci-config.yml` and a
production-ready deployment.

### 8.1 Mandatory Production Settings

| Setting | Quickstart | Production | Why |
|---|---|---|---|
| `dev` | `true` | `false` | Dev mode disables HTTPS enforcement, weakens cookie security, exposes debug info |
| `serve.cookies.secure` | `false` | `true` | Cookies must be Secure in production (HTTPS) |
| `oauth2.hashers.bcrypt.cost` | `4` | `12` | Cost 4 is instant to brute-force; 12 is the minimum for production |
| `oauth2.expose_internal_errors` | `true` | `false` | Internal errors leak implementation details to clients |
| `log.level` | `debug` | `info` or `warn` | Debug logging is verbose and may log sensitive data |
| `secrets.system` | hardcoded | generated, ≥32 chars | See Part 4 (Secrets) |
| `secrets.cookie` | hardcoded | generated, ≥32 chars | Separate from system secret |
| `oidc.subject_identifiers.pairwise.salt` | hardcoded | generated, ≥8 chars, immutable | Never change after first deployment |

### 8.2 TLS Termination

Hydra supports built-in TLS (`serve.tls`) but in the bar ecosystem, TLS is
terminated at the ingress controller (ALB or nginx). Hydra listens on plain
HTTP inside the cluster. The ingress handles certificates (ACM for ALB, or
cert-manager for nginx).

Ensure:
- The ingress forwards `X-Forwarded-Proto: https` so Hydra knows the
  external scheme is HTTPS (required for `SameSite=None` cookies and issuer
  URL validation).
- The `urls.self.issuer` and `urls.self.public` use `https://` scheme.

### 8.3 Resource Limits and Probes

The Pulumi deploy module should set K8s resource requests/limits and health
probes:

```yaml
resources:
  requests:
    cpu: 100m
    memory: 128Mi
  limits:
    cpu: "1"
    memory: 512Mi

livenessProbe:
  httpGet:
    path: /health/alive
    port: 4445
  initialDelaySeconds: 5
  periodSeconds: 10

readinessProbe:
  httpGet:
    path: /health/ready
    port: 4445
  initialDelaySeconds: 5
  periodSeconds: 5
```

The `/health/alive` endpoint returns 200 when the process is running. The
`/health/ready` endpoint returns 200 only when the database connection is
healthy. Both are on the admin port (4445).

### 8.4 Replicas and Availability

Hydra is stateless (all state is in the database). Run multiple replicas for
availability:

| Environment | Replicas | Anti-affinity |
|---|---|---|
| sandbox | 1 | none |
| devel | 1 | none |
| stage | 2 | preferred (spread across AZs) |
| prod | 3 | required (spread across AZs) |

Use `topologySpreadConstraints` or `podAntiAffinity` in the Deployment spec.

### 8.5 Network Policies

Hydra has two ports with different trust levels:

| Port | Name | Trust | Access |
|---|---|---|---|
| 4444 | public | untrusted | Wallets, browsers, external clients via ingress |
| 4445 | admin | internal | Consent app, credential issuer, migration job only |

The admin port must never be exposed to the internet. Use K8s NetworkPolicy
to restrict access to port 4445:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: hydra-admin-access
spec:
  podSelector:
    matchLabels:
      app: hydra
  ingress:
    - from:
        - podSelector:
            matchLabels:
              app: consent-app
        - podSelector:
            matchLabels:
              app: credential-issuer
        - podSelector:
            matchLabels:
              job-name: hydra-migrate
      ports:
        - port: 4445
    - ports:
        - port: 4444
```

### 8.6 Database Connection Tuning

The DSN should include connection pool parameters:

```
postgres://hydra:<password>@<host>:5432/hydra?sslmode=require&max_conns=20&max_idle_conns=4
```

For Aurora:
- Use `sslmode=require` (Aurora enforces TLS)
- Use IAM authentication if available (via `pg-creds-aurora` sidecar from bar
  framework, same pattern as billing/url-shortener)
- Set `max_conns` based on replica count × expected concurrency (Aurora
  Serverless v2 scales connections automatically)

### 8.7 Observability

Hydra supports OpenTelemetry tracing via `ory/x/otelx`. Configure in the
YAML config:

```yaml
tracing:
  provider: otel
  service_name: hydra
  providers:
    otlp:
      server_url: otel-collector.monitoring.svc:4317
      insecure: true
```

Metrics are exposed via the admin port. For Prometheus scraping, add
annotations to the Deployment pod template:

```yaml
annotations:
  prometheus.io/scrape: "true"
  prometheus.io/port: "4445"
  prometheus.io/path: "/admin/metrics/prometheus"
```

### 8.8 Wallet Attestation Trust Anchors

In production, the `wallet_attestation.trust_anchors` must contain the real
root CA certificates of the wallet providers you trust. The quickstart uses a
self-signed test CA generated by `test/oidc4vci-external/gen-attester-jwks.sh`.

For HAIP conformance, the trust anchor is the root CA of the wallet provider's
PKI. Each wallet provider publishes their root CA. You add it to the config
and register a client with `token_endpoint_auth_method: attest_jwt_client_auth`
and `client_id` matching the wallet provider's `sub` claim.

## Part 9: Connecting Hydra to the OIDC4VCI Deployment

The eudi project (oidc4vp-connector, oidc4vp-verifier, oidc4-demo) currently
operates independently of Hydra. Connecting them means making Hydra the
Authorization Server that the Credential Issuer and Wallet interact with.

### 9.1 Integration Points

```
┌──────────────┐     ┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│   Wallet     │────→│  Hydra AS    │────→│ Consent App  │────→│   Kratos     │
│              │     │ (public:4444)│     │ (port 3000)  │     │ (identity)   │
│              │     │ (admin:4445) │     │              │     │              │
└──────┬───────┘     └──────┬───────┘     └──────────────┘     └──────────────┘
       │                    │
       │                    │ introspect + preauth API
       ▼                    ▼
┌──────────────┐     ┌──────────────┐
│  Credential  │────→│  Hydra Admin │
│  Issuer      │     │  (port 4445) │
│  (mock or    │     └──────────────┘
│   real)      │
└──────────────┘
```

The Credential Issuer needs:
1. Network access to Hydra admin port (4445) for `POST /admin/oauth2/preauth`
   and `POST /admin/oauth2/introspect`
2. Its `authorization_servers` metadata to point to Hydra's public URL
3. Optionally, a Token Hook webhook endpoint that Hydra calls

The Consent App needs:
1. Network access to Hydra admin port (4445) for login/consent challenge
   accept/reject
2. `HYDRA_ADMIN_URL` env var pointing to `http://hydra-admin:4445`
3. Ability to handle `authorization_details` in consent challenges (see
   `docs/integration/consent-app-authorization-details.md`)

### 9.2 What Changes in the eudi Pulumi Deploy

The eudi deploy programs (`eudi/deploy/*/main.go`) currently deploy the
oidc4vp-connector, oidc4vp-verifier, and oidc4-demo. To connect Hydra:

**Option A: Co-deploy in the same namespace (recommended for initial integration)**

Add Hydra as a dependency in the eudi deploy program. The eudi deploy calls
`pulumihydra.DeployK8s()` in addition to its own resources:

```go
// In eudi/deploy/devel/main.go — after deploying oidc4vp components

// Deploy Hydra AS in the same namespace
hydraArtifacts, err := pulumihydra.LoadArtifacts(c.Context(), logger, artifactBaseDir)
if err != nil {
    return fmt.Errorf("load hydra artifacts: %w", err)
}

hydraResources, err := pulumihydra.DeployK8s(c, &pulumihydra.DeployK8sArgs{
    Deploy:      deploy,
    Logger:      logger,
    AWSProvider: infra.awsProvider,
    K8sProvider: infra.k8sProvider,
    Namespace:   pulumi.String(deploy.Namespace()),
    Artifacts:   hydraArtifacts,
    Tags:        infra.tags,
    // Hydra-specific config
    IssuerURL:       pulumi.Sprintf("https://hydra.%s.truvity.tech", environment),
    ConsentAppURL:   pulumi.Sprintf("http://%s-%s-consent:3000", releaseName, projectName),
    DSN:             dsnSecret,  // from Secrets Manager
})
```

The Credential Issuer (mock-issuer or real) is configured to point to Hydra:

```go
// Credential Issuer env vars
"MOCK_ISSUER_AUTH_SERVER_URL":       pulumi.Sprintf("https://hydra.%s.truvity.tech", environment),
"MOCK_ISSUER_AUTH_SERVER_ADMIN_URL": pulumi.String("http://hydra-admin:4445"),
```

**Option B: Separate Pulumi stack (recommended for production)**

Hydra gets its own Pulumi stack (`hydra/deploy/*/main.go`) and the eudi stack
references it via K8s service DNS:

- Hydra admin: `http://hydra-admin.hydra.svc.cluster.local:4445`
- Hydra public: `http://hydra-public.hydra.svc.cluster.local:4444`

The eudi connector config points to these URLs. Cross-namespace access requires
either no NetworkPolicy or explicit allow rules.

### 9.3 Consent App Deployment

The Consent App (`hydra-login-consent-node`) must be deployed alongside Hydra.
It's a Node.js app that handles login/consent UI delegation.

In the bar ecosystem, the consent app is another Docker image. Add it to
`cfg/registry.yaml`:

```yaml
- name: ory
  ecr:
    - hydra
    - consent-node    # hydra-login-consent-node
  s3: []
```

The consent app needs:
- `HYDRA_ADMIN_URL` — Hydra admin endpoint (K8s service URL)
- Ingress for the login/consent/logout URLs configured in Hydra's `urls.*`

For OIDC4VCI, the consent app must handle `authorization_details` correctly.
See `docs/integration/consent-app-authorization-details.md` for the full
contract. The reference implementation in `hydra-login-consent-node` already
does this.

### 9.4 Client Registration

After Hydra is deployed, register OAuth2 clients for the Credential Issuer
and Wallet. This can be done via:

1. A Pulumi post-deploy step that calls the admin API
2. A K8s Job that runs after Hydra starts
3. Manual registration via `curl` or the Hydra CLI

Example for a wallet-attestation client:

```bash
curl -X POST http://hydra-admin:4445/admin/clients \
  -H "Content-Type: application/json" \
  -d '{
    "client_id": "https://wallet.example.org",
    "token_endpoint_auth_method": "attest_jwt_client_auth",
    "grant_types": [
      "authorization_code",
      "urn:ietf:params:oauth:grant-type:pre-authorized_code",
      "refresh_token"
    ],
    "response_types": ["code"],
    "scope": "openid offline",
    "redirect_uris": ["https://wallet.example.org/callback"]
  }'
```

### 9.5 DNS and Ingress

Hydra needs two DNS entries per environment:

| DNS Record | Target | Purpose |
|---|---|---|
| `hydra.<env>.truvity.tech` | Ingress (public port 4444) | Wallet-facing OAuth2 endpoints |
| `consent.<env>.truvity.tech` | Ingress (consent app port 3000) | Login/consent UI |

The admin port (4445) is internal-only — no DNS or ingress needed.
